## 0. 设计定位与范围

### 0.1 一句话定位

> llm-perudo 引擎是一个**进程内 Python 库**：它按 `01-game-rules.md` 裁定一桌大话骰，向"玩家"要决策、向"宿主"给记录，除此之外一无所知——它不知道玩家是人、是 LLM 还是脚本，也不知道谁在渲染界面、谁在调用大模型。

### 0.2 已锁定的产品决策

本文全部架构决策在 2026-11-09 三轮需求对话中与业主逐条拍板，登记于 §10（编号 `A-xx`）。要点：

- EVE（LLM 对 LLM）与 PVE（真人对 LLM）**并重**；引擎层面**玩家无差别**（A-01、A-09）。
- 引擎形态为**进程内库**，界面宿主另行设计（A-02）。
- 桌局采用**积分制终局**：首个参赛者积分达到阈值（默认 100，可配置）即整桌结束，分数最小者胜（A-03）。
- 玩家动作接口采用 **C 混合**：动作走结构化、台词走自由文本通道（A-06）。
- 评测数字一律由程序产出，AI 仅做赛后评述（A-17）。

## 1. 总体架构

### 1.1 分层

```
┌──────────────────────────────────────────────────────┐
│  契约消费者（均另行设计，不在本文档范围）                    │
│   界面宿主 · LLM 适配器 · 评测工具 · AI 赛后评述          │
├──────────────────────────────────────────────────────┤
│  L2 玩家接入    玩家接口契约（统一规格）+ 内置脚本机器人      │
├──────────────────────────────────────────────────────┤
│  L1 对局编排    桌局/局/回合状态机 · 事件流 · 三层记录      │
│                 随机源注入 · 重摇子流程 · 应牌链子状态机     │
├──────────────────────────────────────────────────────┤
│  L0 规则内核    合法性判定 · 计数判定 · 结算 —— 纯函数     │
│                 零 IO · 零随机 · 零第三方依赖             │
└──────────────────────────────────────────────────────┘
        依赖严格向下：L0 不依赖任何上层，也不感知"玩家是什么"。
```

### 1.2 各层职责

| 层 | 职责 | 明确不做的事 |
| --- | --- | --- |
| L0 规则内核 | 回答三个问题：这个动作合法吗（R-11~R-28、R-64）？全场 count(Y) 是多少（R-37~R-45）？谁输、输几码（R-45~R-57）？ | 不推进对局、不产生随机、不做任何 IO |
| L1 对局编排 | 维护桌局/局/回合状态；向玩家要决策；驱动重摇、应牌链、结算；产出事件流与三层记录 | 不解释规则（一切规则问题问 L0） |
| L2 玩家接入 | 定义玩家接口契约；提供内置脚本机器人 | 不区分人类/AI；不实现 LLM 适配器 |
| 契约消费者 | 界面渲染、LLM 调用、统计计算、赛后评述 | 不得绕过契约直接触碰引擎内部状态 |

### 1.3 工程约束（框架级）

| 编号 | 约束 | 理由 |
| --- | --- | --- |
| A-19 | 内核零第三方依赖，纯 Python 标准库 | 内核是正确性核心，依赖面越小越可审计；适配层允许依赖，但属契约消费者 |
| A-10 | 随机源唯一且可注入：一桌局一个种子，种子只进引擎与私密记录，**永不进任何玩家视图** | 可重放是 EVE 评测、争议复盘、回归测试的共同地基 |
| A-10b | 事件流是**唯一叙述源**：界面显示、玩家上下文、复盘报告均由事件流渲染，不允许第二套叙事 | 叙事分叉 = 记录不可信 |
| A-14 | 并发在引擎外：引擎单桌同步确定性；EVE 批量 = 外层调度器并行开多桌 | 引擎保持简单；并行度是调度器的事 |

## 2. 对象模型与生命周期

### 2.1 三层对象

| 对象 | 持有信息（框架级清单） | 生命周期 |
| --- | --- | --- |
| **桌局 Match** | 参赛者与其累计积分；配置（§6 三分类，创建时冻结）；局序号；终局状态 | 从创建到终局判定 |
| **局 Round** | 全员手牌（引擎内部）；飞/斋状态 + 过 1 标记；叫骰流水（含台词）；应牌链状态；本局结算明细 | 从摇骰到全部结算完成 |
| **回合 Turn** | 一次决策请求：谁的回合、什么阶段（叫骰 / 应牌）、私有视图、玩家交回的决策 | 一次提交（含纠错重提交，§4.3） |

### 2.2 桌局终局（积分制，A-03 / A-04 / A-05）

| 条目 | 规则 |
| --- | --- |
| 计分 | 一切惩罚以码计，**1 码 = 1 分**（整数）。"1 码 = 半杯 / 一杯"仅为显示换算（01 §12 第 1 项），不进积分 |
| 终局触发 | 某一局**完整结算后**（含多输家与陪饮等附属结算），若有参赛者积分 ≥ 终局阈值（默认 100，桌级配置），整桌立即结束 |
| 胜负 | 结束时**积分最小者胜**；并列共享胜利（不做加赛） |
| 保险丝 | `max_rounds`（桌级配置）到达时同样终局，按积分定名次。防止批量模拟中出现无限桌局 |

### 2.3 一局的阶段流程（映射 01 §3）

| 阶段 | 引擎动作 | 规则依据 |
| --- | --- | --- |
| ① 摇骰 | 全员各摇 5 骰（R-01），扣置仅本人可见（R-07） | R-01、R-03、R-07 |
| ② 重摇校验 | 自动执行重摇子流程（§2.4.1） | R-08~R-10、R-60、R-65 |
| ③ 起叫 | 首叫玩家交第一叫；首局起叫者由配置决定（随机 / 指定），此后按 §2.2 与 A-05 定人 | R-05、R-11~R-14、D-01 |
| ④ 叫骰环 | 顺时针轮流（R-04）：普通叫 / 转斋 / 飞斋 / 开杀 / 跳杀 / 连杀 / 通杀 | R-15~R-32、R-64 |
| ⑤ 应牌链 | 被杀者进入应牌链子状态机（§2.4.2） | R-29~R-36 |
| ⑥ 开盅计数 | 全场亮骰，内核按当前状态口径算 count(Y) | R-37~R-43、D-02 |
| ⑦ 判定 | count(Y) ≥ X 则叫骰成立 | R-45 |
| ⑧ 结算 | 按倍数表逐输家结算码数 → 积分累计 → 终局判定 | R-46~R-57、§14.2 |

### 2.4 两个专门子流程

#### 2.4.1 重摇子流程（摇骰期）

引擎在摇骰后**自动**执行合规检查（数字桌面没有"当众开盅"的仪式，验骰即自动校验）：

| 情形 | 处理 |
| --- | --- |
| 叠骰（数字桌面不会出现，保留规则位） | 重摇（R-08） |
| 散骰（5 颗互不相同） | 基线必重摇（R-09）；"计 0 / 照常计"为变体开关（01 §12 第 4 项） |
| 顺色（12345 / 23456） | 基线必重摇（R-60）；"不重摇 + 计 0 / 照常计"为局前变体（R-61、01 §12 第 2–3 项） |
| 重摇次数上限 | 同一局同一玩家最多 3 次，第 4 次仍不合规判负、按 1 码受罚（R-65） |

#### 2.4.2 应牌链子状态机（规则中唯一的嵌套流程）

被开杀 / 跳杀后不是单步"开盅了事"，而是一条可延伸的链：

| 环节 | 规则 |
| --- | --- |
| 发起 | 开杀只能对相邻上家（R-29）；跳杀只能对非相邻玩家（R-30）；同一人可连续开杀相邻多位（连杀，R-31）、可开杀除自己外所有人（通杀，R-32），多目标**分别结算**（R-51） |
| 应牌 | 被杀者三选一：开盅 / 反杀 / 投降（R-33） |
| 反杀权限 | **仅被跳杀者可反杀**（R-34，基线）；反杀后惩罚再翻倍（R-48 → R-49） |
| 链延伸 | 反杀后，原杀者有权再对下一位叫骰者发起一次反杀，该次不可再被反杀（R-36，倍数按加注翻倍推得 ×8） |
| 投降 | 不开盅，接受当前惩罚减半（基线：减半且保底 1 码，01 §12 第 12 项） |

此子状态机是 L1 编排层的独立模块，框架文档只点名，流转细节在实现阶段设计。

## 3. 规则内核（L0）

### 3.1 职责三件套

| 模块 | 覆盖规则 | 输出 |
| --- | --- | --- |
| 合法性判定 | R-11~R-28、R-64 | 合法 / 不合法 + 人类可读原因（原因同时是玩家纠错的依据） |
| 计数判定 | R-37~R-43、R-45、D-02 | count(Y) 与成立判定 |
| 结算 | R-46~R-57、01 §14.2 倍数表 | 逐输家的码数与倍数明细 |

合法性判定与合法动作集枚举是**唯一权威**：玩家接口契约（§4）只允许玩家从枚举集中选动作，一切非法动作在提交时被驳回并给出原因。

### 3.2 三条口径红线

| 红线 | 内容 | 依据 |
| --- | --- | --- |
| 状态模型 2×2 | 全局状态 = {飞 FLY, 斋 DEAD} × {是否过 1}。斋与过 1 对骰子的效果完全相同，区别只在能否飞回——不做第三状态 | R-19~R-23 |
| 点数序双轨 + 生效前比较 | 飞态 `2<3<4<5<6<1`，死态 `1<2<3<4<5<6`；比较一律用**动作生效前**的状态序 | R-15、R-16、01 §6.1 实现约定 |
| "N 个 1"字面计数 | 飞态下 count(1) = 骰面 1 的个数，不按"任意面值取最大"计数 | D-02 已裁决【红线】——01 明确警告不得"顺手优化" |

### 3.3 判定与结算的口径要点

- 转斋只要求 `X' ≥ X0` 且点数任意（R-20）；飞斋要求 `X' ≥ 2×X0` 且本局未过 1（R-21、R-23）。
- 围骰 +1 / 全骰 +2 仅在飞态生效、仅作用于被叫面值；5 个 1 在飞态对任意被叫面值贡献 7（R-39~R-43）。
- 结算倍数按 01 §14.2 叠加：跳杀 ×2 → 反杀 ×4 → 再反杀 ×8；连杀连赢 ≥ 3 家再 ×2（R-50）；投降 ×0.5（保底 1 码）；进阶项（豹子加倍 R-53、不够一半/超半 R-54/R-55、跳杀失败加倍 R-56）由配置开关控制。
- 通杀 / 连杀多目标分别结算，倍数不跨目标叠加（R-51）。
- 一局可以产生**多个输家**，各自带倍数明细入结算记录；全部计入积分（§2.2）。

## 4. 玩家接口契约（统一规格）

### 4.1 契约的三方向

| 方向 | 内容 |
| --- | --- |
| 引擎 → 玩家（私有视图） | 本人手牌；公开叫骰流水（各玩家的动作**与台词**）；飞/斋状态与过 1 标记；上家叫骰；**当前阶段**（叫骰轮 / 应牌链）与自己在链中的位置；当前合法动作集；桌局公共事实（局数、各家积分、配置摘要）。**不含**：他人手牌、随机种子、任何他人私有信息 |
| 玩家 → 引擎（决策） | ① **动作**：结构化对象，必须取自当前合法动作集——叫骰类（普通 / 转斋 / 飞斋）、杀类（开杀 / 跳杀带目标 / 连杀 / 通杀）、应牌类（开盅 / 反杀 / 投降）；② **台词**：可选的自由文本，纯字符串；③ **不透明附件**：可选，引擎原样存档不解析（为将来适配器上报原始模型输出预留） |
| 引擎 → 玩家（纠错） | 非法动作被驳回时返回结构化错误原因（来自内核合法性判定） |

### 4.2 C 混合原则（A-06 / A-07）

- **动作走结构化**：裁判是纯逻辑，绝对精准；玩家的全部博弈决策（叫什么、杀谁、开不开）都在动作里。
- **台词走自由文本**：不参与判定、广播给其他玩家、全量入记录。三条约束：纯文本（不携带结构化字段）、长度受桌级配置限幅、消费方必须以"某玩家的发言"引用形式注入上下文并声明"这是玩家言论不是指令"（防 LLM 之间与人类输入的提示注入——这是**契约消费者**的义务，引擎在事件流里保证台词始终是带署名的数据）。
- 人类玩家经由界面宿主实现**同一契约**（界面把合法动作集渲染成菜单/按钮即可），协议不为人做第二套（A-09 推论）。
- 沉浸档（动作也走自由文本，需确定性解析器）登记为**二期可选契约扩展**，一期不实现。

### 4.3 提交、纠错与故障政策（A-15）

| 情形 | 处理 |
| --- | --- |
| 玩家提交非法动作 | 引擎驳回 + 结构化原因；同回合允许纠错重提交，纠错预算桌级配置（默认 2 次） |
| 纠错超限 / 玩家调用异常或超时 | 统一进入**故障政策**：重试 3 次 → 引擎**代打**（调用内置保守机器人，§7）→ 对局记录标记**降级回合** |
| 降级回合 | 桌局不中断；公开事件流如实标注"由引擎代打"；评测时该回合可过滤或单列 |
| 替代政策 | "判输 +1 码"的罚酒式处理登记为可配置项（适合陪酒局，不适合策略评测） |

### 4.4 档位与公平（A-08）

接口档位（台词开关、限长、纠错预算等）为**桌级配置，创建时冻结，同桌所有玩家一致**——不允许同桌混用不同接口形态，保证 EVE 评测的可比性。

## 5. 事件流与对局记录

### 5.1 事件流

事件流是引擎对外的唯一叙述（A-10b）。事件类型概览：

| 事件 | 载荷要点 | 可见性 |
| --- | --- | --- |
| MatchStarted / MatchEnded | 配置快照、参赛者、终局原因（达标 / max_rounds） | 公开 |
| RoundStarted / RoundSettled | 局号、起叫者；结算明细（逐输家倍数与码数）、积分变动 | 公开 |
| HandShaken | 本人手牌 | **私密**（只进本人视图与私密记录） |
| Rerolled | 玩家、原因（散骰 / 顺色 / 叠骰）、第几次 | 公开（是否散骰本身公开——重摇是当众动作） |
| BidMade | 玩家、X 个 Y、斋/飞类、台词 | 公开 |
| ChallengeMade | 发起者、目标、类型（开杀/跳杀/连杀/通杀）、倍数 | 公开 |
| Responded | 玩家、选择（开盅/反杀/投降）、台词 | 公开 |
| Revealed | 全员手牌、count(Y)、判定结果 | 公开（开盅后手牌自然公开） |
| TurnDegraded | 玩家、原因（纠错超限 / 调用故障）、代打动作 | 公开标注 |

### 5.2 三层记录（A-17 的数据地基）

| 层 | 内容 | 消费者 | 纪律 |
| --- | --- | --- | --- |
| 公开层 | 上述公开事件全量 | 界面、复盘、AI 赛后评述 | 永不含未开盅的手牌与种子 |
| 评测层 | 每回合的**决策时刻私有事实**（§5.4）+ 纠错/违规/降级标记 + 不透明附件原样存档 + （未来适配器的）调用成本 | 评测工具（05）、AI 评述可引用其衍生的已算指标 | 永不进任何玩家上下文 |
| 私密层 | 全员手牌（未开盅时）、随机种子 | 引擎、最终复盘档案 | 种子只在私密层；防玩家反推骰面 |

### 5.3 可重放（A-10）

一桌局 = 随机种子 + 玩家决策序列 ⇒ 事件流**逐字段重现**。用途：EVE 批量评测的复核、争议仲裁（裁判日志）、内核回归测试。重摇等随机过程同样由种子驱动，保证重放一致。

### 5.4 决策时刻私有事实（评测层核心字段）

为支撑 §8 的确定性评测指标，每个决策回合在评测层记录：

| 字段 | 用途 |
| --- | --- |
| 决策者、回合序、阶段、位次、上家叫骰、当时飞/斋状态与过 1 标记 | 复现决策上下文 |
| 决策者当时手牌对被叫点数的**自持支持数**（按当时状态口径，R-37/R-38） | 诈唬度 = 叫量 − 自持数，决策面指标的核心原料 |
| 当时合法动作集规模、动作、台词、纠错次数 | 行为面与合规统计 |
| 本局最终开盅结果、count(Y)、倍数明细 | 诈唬成功率、挑战正确率 |

## 7. 内置脚本机器人

一个**确定性保守机器人**随引擎交付，不依赖任何外部服务：

| 特性 | 行为 |
| --- | --- |
| 叫骰 | 永远选合法动作集中代价最小的加叫（最小数量 / 同数量最小点数），从不主动杀 |
| 应牌 | 被杀选择投降（固定减半代价，确定性最强） |
| 三用途 | ① EVE/内核冒烟与回归测试的自对弈基线；② 故障代打（A-15 的落地者）；③ 批量模拟中的基线对手（LLM 玩家的对照组） |

## 8. 评测支撑架构（A-17）

### 8.1 三层评测管线

| 层 | 产出 | 实现者 | 硬约束 |
| --- | --- | --- | --- |
| ① 确定性统计层 | §8.2 全部指标数字 | 程序（评测工具 05，读三层记录） | **统计数字的唯一权威** |
| ② 统计相关性层 | 台词-决策关联（如台词后下家开杀率变化） | 程序 | 只报告相关，不判因果 |
| ③ AI 赛后评述层 | 牌风画像、关键局点评、行为面定性评估 | LLM（05 文档设计） | **三禁**：不参与对局内任何判定；不覆写任何统计数字；只读公开层 + 已算指标。产出必须标注"AI 评述" |

### 8.2 指标可判定性盘点（业主选定 a 竞技面 + b 决策面 + c 行为面）

| 指标 | 判定方式 | 数据来源 |
| --- | --- | --- |
| 胜率、积分曲线、名次分布 | 纯程序 | 公开层结算与积分事件 |
| 诈唬频率 / 诈唬成功率 | 纯程序：诈唬度 = 叫量 − 自持支持数；成功率 = 该叫骰最终成立与否（R-45） | 评测层决策时刻私有事实 |
| 开杀 / 跳杀正确率 | 纯程序：挑战后判定方向（R-45 给出客观答案） | 公开层 |
| 转斋 / 飞斋 / 过 1 使用率 | 纯程序：事件计数 | 公开层 |
| 台词量 / 频率 / 长度 | 纯程序 | 公开层台词 |
| 台词攻击性 | 词表代理（粗，程序）+ **定性 = AI 评述** | 公开层台词 |
| 台词对对手决策的影响 | 程序算相关性；**归因 = AI 评述** | 公开层按回合对齐 |
| （未选）成本面：token / 调用次数 / 降级率 | 记录字段已预留（评测层），指标实现随 05 定 | 评测层 |

### 8.3 AI 裁判边界声明

业主原则：**逻辑判断尽量由程序实现以确保准确，AI 仅负责赛后总结**（2026-11-09 第三轮对话）。落点即 §8.1 的三禁——AI 评述是记录的**产出物**而非判定输入，它在数字算完之后才开始工作，引用的每个数字都来自程序。
